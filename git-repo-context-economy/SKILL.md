# Экономия контекста при работе с GitHub-репозиторием

Версия навыка: 2026-11-05 · Исходник: `aero-skills/git-repo-context-economy/SKILL.md` (https://github.com/AeropulseDev/aero-skills). Сверка версии — по правилу `skills-index`.

Применяется всегда, когда предстоит читать/анализировать issues, PR, комментарии или состояние репозитория через `gh`/`git`/GitHub API (в т.ч. через device_bash на компьютере пользователя).

## Правила

1. **Фильтровать на стороне запроса, а не после.** Использовать `since=`, `per_page`, GitHub Search API qualifiers (`is:issue`, `label:`, `milestone:`, `state:`) — никогда не тянуть весь список issues/комментариев, чтобы потом резать его локально или в контексте.
2. **Тяжёлые сквозные операции — в сабагента.** Задачи вида «пройти по N issues/PR и найти X» делегировать через Agent-тул отдельному агенту с явной инструкцией вернуть только релевантные строки/номера коротко. Сырые данные остаются в контексте сабагента, не в основном чате.
3. **Батчить независимые запросы.** Несколько независимых вызовов API/CLI (repo info, protection, labels, milestones, issues count, права токена и т.п.) отправлять одним проходом/одним сообщением с параллельными tool calls, а не последовательно.
4. **Состояние и решения — в постоянное хранилище, не в истории чата.** Если сессия привязана к Project (claude.ai) — писать туда сводку/decisions log (`project_write`) вместо того, чтобы держать полный разбор issues в переписке. Следующий заход читает сводку, а не поднимает весь репозиторий заново. Если Project не привязан — предложить файл в репозитории (например `team-setup/decisions_log.md`).
5. **Не перечитывать то, что не менялось.** `git fetch`, полные дампы issues/PR или широкий grep по всем issues делать только когда реально ожидается новое (кто-то ответил, статус сменился) — не «на всякий случай».
6. **Различать, где физически выполняется команда.** Если сессия работает через мостик к компьютеру пользователя (remote-devices/device_bash), каждая git/curl-команда выполняется на этой машине её сетью и её git — это важно для диагностики сетевых ограничений и для понимания, где хранятся токены/credentials.

7. **Публиковать в GitHub текстом, который он сам рисует.** Схемы в issue, PR и `.md` — блоком ```` ```mermaid ```` (GitHub рисует его сам, читатели без доступа к закрытым репозиториям видят схему, ИИ-агенты читают её как текст). Картинки (SVG/PNG) — только дополнением со ссылкой: картинка из закрытого репозитория видна лишь его участникам, а агенту стоит токенов зрения. Готовые блоки схем инфоцентра — `out/wf/<id>.mermaid.md` (навык infocenter). Таблицы — Markdown-таблицами, код и команды — блоками с языком.
8. **Длинное — файлом `.md`, в комментарии — суть и ссылка.** Большой разбор, спецификацию или отчёт класть файлом в репозиторий (или PR) и давать в комментарии 5–10 строк и ссылку: файл читается и правится по частям, его можно сравнить по версиям, агент берёт только нужный раздел (`grep`/`sed -n`), а не весь тред.
9. **Читать исходник, а не картинку.** Если у схемы или отчёта есть текстовый исходник (`.mermaid.md`, `.wf.txt`, `.md`), читать его; картинку открывать, только когда нужен именно вид.

## Когда не применять жёстко

Если задача разовая и маленькая (посмотреть один issue, один PR) — обычного точечного запроса достаточно, не нужно городить сабагента или сводку ради одного обращения.
